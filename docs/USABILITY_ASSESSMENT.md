# Shoplazza CLI 易用性评估方法论

评估对象：`/usr/local/bin/shoplazza`（npm 安装，实测版本 2.0.7，2026-07-14）
评估范围：全部命令面 —— `+shortcut`（高频封装）、自动生成的 `<command>`（OpenAPI 全参数）、`api rest`（兜底）
评估角度：① AI Agent 使用 ② 开发者/商家命令行使用

---

## 0. 已知的结构特征（评估前置观察）

- 三层命令模型：`orders +search`（智能默认）/ `orders list`（全参数）/ `api rest GET ...`（兜底）
- `schema <module>.<command>` 可自省参数/请求体/响应结构
- 默认输出 JSON，可切 `--format pretty|table`
- 支持 `--dry-run` 打印请求而不发送
- `auth status` 返回结构化 JSON（含 `logged_in`, `granted_scopes`, `profiles`）
- 顶层 15 个业务模块（api/app/auth/billing/checkout-extension/customers/discounts/orders/products/profile/schema/shop/theme-extension/themes/update/webhook）

这些是"设计上声称的"能力，评估的核心是验证这些能力在**真实使用**中是否兑现。

---

## 1. 评估方法总览

采用「结构化指标扫描」+「盲测任务验证」两阶段，互相印证：

| 阶段 | 方式 | 目的 |
|---|---|---|
| A. 结构化指标扫描 | 我直接执行命令、读输出，逐项打分 | 快速、可重复，覆盖广度 |
| B. 盲测任务 | 派无先验知识的 subagent 独立完成任务 | 验证真实可用性，暴露扫描发现不了的摩擦点 |

两阶段结果冲突时（如指标扫描认为 `--help` 完整，但盲测 agent 仍然卡住），以盲测结果为准，并记录冲突本身作为发现。

## 2. 维度一：AI Agent 可用性

### 2.1 结构化指标 checklist

| 编号 | 指标 | 检查方法 | 合格标准 |
|---|---|---|---|
| A1 | JSON 输出可解析性 | 对代表性命令（每模块至少1个）执行并 `jq .` | 100% 合法 JSON，无需清洗 stdout |
| A2 | stdout/stderr 分离 | 对成功/失败两种情况分别检查 | 数据在 stdout，进度/警告/提示在 stderr |
| A3 | 错误结构化 | 触发常见错误（缺参数/无权限/无效ID/未登录） | 错误也是结构化 JSON（非裸 panic/裸文本），含可操作的字段（如 `error`, `hint`, `code`） |
| A4 | 退出码规范 | 检查 `$?` | 成功 0，不同错误类型退出码有区分 |
| A5 | `--help` 可自举发现 | agent 完全不看文档，只用 `--help` 链式下钻能否找到目标命令 | 3 层以内（顶层→模块→子命令）能定位 |
| A6 | `schema` 自省是否够用 | 用 `schema <module>.<command>` 替代读文档 | 能拿到参数名/类型/是否必填/响应结构，无需猜 |
| A7 | `--dry-run` 可靠性 | 对写操作命令跑 dry-run，比对真实请求 | dry-run 展示的请求与实际发出的一致 |
| A8 | 幂等 & 安全试错 | 对写操作反复试参数是否有副作用风险提示 | 危险操作有二次确认或明确警示 |
| A9 | 命令自描述性 | 命令/flag 命名是否不需要文档就能猜对语义 | 常见操作命名符合直觉（如 `+search` vs `list`） |
| A10 | skills/ 目录对 agent 的指导价值 | 读 `skills/` 下的 md，判断是否覆盖了 A5/A6 覆盖不到的隐藏知识 | 存在且与实际命令行为一致（未过期） |

打分：每项 1-5 分（1=完全不可用，5=开箱即用无摩擦），附证据（实际命令+输出片段）。

### 2.2 盲测任务设计

派 2 个完全不知道 shoplazza CLI 存在的 subagent（Explore 或 general-purpose 类型），只给任务目标，不给任何命令提示，观察它们能否只靠 `--help`/`schema`/报错信息自主完成：

- **任务1（读+简单写，跨模块）**："查询最近一个未处理的订单，并生成对应的物流跟踪更新" —— 需要发现 `orders +search`、`orders +update-tracking` 或原生 command
- **任务2（探索型，代表复杂写操作）**："给某个商品创建一个九折的优惠券，限制仅限某个折扣分组" —— 需要在 `discounts` 模块下自主下钻并处理必填参数

评估指标（每个任务）：
- 是否在无人工提示下完成
- 用了几次试错命令（含失败尝试次数）
- 是否被结构化错误正确引导纠正，还是靠猜
- 是否绕开了预期的 `+shortcut` 走了更繁琐的路径（说明 shortcut 发现性不足）
- 是否出现"因为输出不可解析/文档不一致而卡住"的情况

## 3. 维度二：开发者/商家命令行可用性

### 3.1 结构化指标 checklist

| 编号 | 指标 | 检查方法 | 合格标准 |
|---|---|---|---|
| B1 | 首次上手体验（time-to-first-success） | 全新环境（未登录）到完成一次典型只读查询的步骤数 | ≤3 步，且每步都有明确下一步提示 |
| B2 | 认证流程顺畅度 | 走一遍 `auth login`/`profile` 流程 | 报错/引导清晰，无需查文档 |
| B3 | 错误提示对人类友好 | 故意犯典型错误（拼错子命令、缺必填参数、权限不足） | 报错说明"是什么问题+怎么修"，而非只报 API 原始错误码 |
| B4 | 输出可读性 | 对比 `--format json` vs `pretty` vs `table` | pretty/table 在终端下真正提升可读性，而非仅换个缩进 |
| B5 | README/README.zh 与实际行为一致性 | 抽查 README 中的示例命令实跑 | 示例命令可直接复制执行成功 |
| B6 | 命令记忆负担 | 统计常见商家任务所需敲击的命令长度/参数个数 | 高频操作有 `+shortcut` 覆盖，无需记复杂 flag |
| B7 | 一致性（跨模块） | 抽查 3+ 模块的同类操作（如各自的 `list`/`get`/`+search`） | flag 命名、分页参数、输出结构风格统一 |
| B8 | Tab 补全/发现性 | 检查是否提供 shell completion | 有 `completion` 命令或安装脚本自动配置 |
| B9 | 版本/更新体验 | 跑 `shoplazza update` | 更新流程清晰、不需要额外知识 |

### 3.2 端到端场景测试

以商家真实身份视角，走完整业务闭环（而非单条命令），记录每一步的摩擦：

- **场景1**：全新安装 → 登录 → 查看店铺信息 → 查询近7天订单 → 导出为可读格式
- **场景2**：给某商品打折 → 验证折扣生效 → 撤销折扣（测试"发现如何撤销"的难度）

## 4. 严重程度分级与报告格式

沿用团队 code-review 的分级标准：

| 级别 | 含义 |
|---|---|
| CRITICAL | 导致任务完全无法完成，或数据/资金风险（如无警示的破坏性操作） |
| HIGH | 显著增加试错成本或造成误解，但存在绕行路径 |
| MEDIUM | 影响体验但不阻塞任务 |
| LOW | 细节打磨类问题（措辞、格式一致性等） |

最终报告结构（写入本文件的「评估结果」章节，或另建 `USABILITY_FINDINGS.md`）：

```
## 发现 #N [严重程度]
- 维度：AI Agent / 开发者商家
- 指标编号：A3 / B2 ...
- 现象：<实际命令 + 实际输出>
- 影响：<谁会卡在这里，卡多久>
- 建议：<具体可执行的修复方向>
```

每个维度最后附一个 1-5 分的总分和一句话结论。
